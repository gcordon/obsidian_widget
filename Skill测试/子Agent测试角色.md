# 子 Agent 测试角色

## 用途

为 Skill 行为测试提供统一的子 Agent 角色、信息边界和执行顺序。

具体测试用例、预期行为和执行记录保存在对应的测试文件中。本文件只定义测试如何组织，不保存某个 Skill 的测试答案。

## 核心原则

- 主 Agent 是测试负责人，负责读取完整测试用例、调度角色、汇总证据和与用户确认。
- 子 Agent 只接收完成当前角色所需的最少信息。
- 执行者不知道预期答案，审查者不参与执行，修复分析员不能直接修改 Skill。
- 子 Agent 不得读取完整测试文件、其他角色结论或尚未确认的修复方案。
- 测试过程中不覆盖 Skill、测试素材、案例文件或其他 Agent 的输出。
- 涉及真实生图时，继续遵守项目的逐次方案汇总和“开始生图”授权规则。

## 角色

### 主 Agent：测试负责人

负责：

1. 读取目标 Skill、共享角色文件和具体测试文件。
2. 选择测试用例并准备原始输入素材。
3. 按阶段启动所需子 Agent，不把完整测试文件交给子 Agent。
4. 保存各角色的原始结果，区分流程问题、图片问题、模型随机性和测试问题。
5. 测试失败时执行项目规定的 Skill 修复门禁。

不得把审查结论、怀疑点或预期答案提前提供给盲测执行者。

### `blind-runner`：盲测执行者

负责使用目标 Skill 处理原始用户请求，返回真实执行过程和产物。

只提供：

- 目标 Skill 名称或路径
- 原始用户请求
- 原始输入素材
- 本次任务必需的输出要求

禁止提供：

- 预期行为和禁止行为
- 已知问题或怀疑点
- 评分标准
- 修复方案
- 其他 Agent 的结论
- 完整测试文件

提示词模板：

```text
使用 <目标 Skill> 处理下面的真实用户请求。

用户请求：
<原始用户请求>

输入素材：
<原始素材路径或附件>

只按照 Skill 和用户请求正常执行。不要读取任何测试文件，不要评价或修改 Skill。返回原始执行过程、回复和产物。
```

### `process-auditor`：流程审查员

负责对照测试标准检查执行过程，包括 Skill 触发、分析顺序、授权、提示词和修改边界。

只提供：

- 盲测执行记录
- 本用例的预期行为
- 本用例的禁止行为

不得修改 Skill，不评价图片审美，不提出未经证据支持的修复方案。

提示词模板：

```text
审查下面的执行记录，只判断流程是否符合本用例要求。

执行记录：
<blind-runner 原始记录>

预期行为：
<预期行为>

禁止行为：
<禁止行为>

输出：流程结果（通过/失败）、逐项证据、无法判断项。不要修改 Skill。
```

### `visual-auditor`：视觉审查员

只在存在真实生成结果时使用。负责比较权威参考图与当前稿，检查元素、文字、构图、颜色、比例、位置、背景和多余内容。

只提供参考图、生成结果和基础视觉验收项；不提供预设修复结论。

提示词模板：

```text
比较 Image 1 权威参考图和 Image 2 当前稿。

仅检查：元素、文字、构图、颜色、比例、位置、背景和多余内容。
输出：图片结果（通过/失败）、可观察差异、无法确认项。
不要提出创意建议，不要修改图片或 Skill。
```

### `red-team`：边界挑战者

负责设计可能诱发误触发、越权生成、沿用旧授权或扩大修改范围的原始用户请求。

只生成测试输入，不执行测试、不评价结果、不提出修复方案。主 Agent 审核后再决定是否加入测试清单。

提示词模板：

```text
针对 <目标 Skill 的职责和边界>，设计少量真实、自然的边界用户请求。
重点覆盖误触发、跳过确认、沿用旧授权和扩大操作范围。
只输出原始用户请求及其测试目标，不执行任务，不提出修复方案。
```

### `repair-analyst`：修复分析员

只在主 Agent 已确认测试存在失败证据后使用。负责判断失败是否属于 Skill，并提出最小修复建议。

必须输出：

- 实际表现
- 预期表现
- 判断为 Skill 问题的依据
- 建议修改的具体规则
- 完整修复提示
- 可能影响的现有流程
- 修改后应重跑的用例

不得直接修改 Skill 或测试文件。主 Agent 必须先把修复说明提交给用户，获得确认后才能实施。

## 阶段搭配

### 低成本流程测试

使用 `blind-runner` 和 `process-auditor`。需要扩展边界时，再使用 `red-team`。

### 真实生图测试

使用 `blind-runner`、`process-auditor` 和 `visual-auditor`。真实生成仍需用户对该次方案明确回复“开始生图”。

### 失败分析

先由主 Agent 汇总执行记录和审查证据，再使用 `repair-analyst`。未获得用户修复确认前，不修改 Skill。

## 标准顺序

1. 主 Agent 选择测试用例并隔离测试答案。
2. `blind-runner` 使用原始请求和素材执行。
3. `process-auditor` 独立检查流程。
4. 有真实图片时，`visual-auditor` 独立检查图片。
5. 主 Agent 汇总结论并更新测试记录。
6. 失败时先解释问题；需要修改 Skill 时，再进入修复门禁。
