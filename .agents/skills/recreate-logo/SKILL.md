# Recreate Logo

## 执行原则

- 把任务视为参考图还原，不视为 Logo 重新设计。
- 把 Image 1 视为唯一权威参考；生成稿只能作为待检查或待修正的当前稿。
- 优先交付简单、合格、可检查的结果，再根据真实差异逐轮修正。
- 不把任何单一案例的图形、文字、颜色或特殊轮廓写入通用流程。
- 图片分析和需求整理时，同时加载并遵循 `imagegen` Skill。
- 图片生成统一使用 `gpt-image-2`。
- 一次只生成一张 Logo；未经授权不得调用图片生成工具。

## 生图前确认

在每次调用图片生成工具前执行以下步骤：

1. 与用户讨论本次目标、输出尺寸、格式、背景以及画面结构。
2. 只有用户明确确认的尺寸、格式和背景才能写入最终提示词；未确认的参数只作为候选方案向用户询问。
3. 参数确认后，填写最终提示词并汇总本次调用的完整生图方案。若涉及多张图片，分别说明每张图片的方案，但每次工具调用仍只生成一张 Logo。
4. 参数确认不等于生图授权。只有用户在该次完整方案汇总后明确回复“开始生图”，才调用生成工具。
5. 只把授权用于该次已汇总的方案。新增、修改或再次生成图片时，重新汇总方案并重新获得“开始生图”授权。

不得把用户更早的授权、宽泛的“继续”或对上一张图片的确认视为本次生图授权。

## 通用首稿提示词

```text
Use case: logo-brand
Asset type: faithful Logo recreation

Input images:
Image 1 is the only authoritative reference.

Primary request:
先在内部认真分析 Image 1，然后完整还原其中所有可见内容。

必须匹配：
- 构图和图形元素
- 文字及字体效果
- 配色和视觉效果
- 比例、位置、间距和留白
- 图层顺序和遮挡关系
- 背景
- 画布宽高比

保持参考图原有风格。
参考图中存在的渐变、阴影、纹理、描边或立体效果应保留；
参考图中不存在的效果不得自行添加。

Constraints:
不要重新设计、简化或美化。
不要增加、删除或替换任何元素。
不要添加额外文字、图标、边框或水印。
文字必须逐字准确。
最终结果应尽可能接近 Image 1。

Output:
<填写本次确认的尺寸、格式和背景要求>
```

只有用户明确确认的尺寸、格式和背景才能替换 `Output` 占位；未确认时保持占位，只提出候选方案并等待确认。不要加入案例之外的创意指令。

## 通用修正提示词

```text
Input images:
Image 1 is the only authoritative reference.
Image 2 is the current draft.

比较 Image 1 与 Image 2，只修正当前稿中最明显的 1—3 个差异。

本轮修正：
1. <具体差异与目标状态>
2. <具体差异与目标状态>
3. <具体差异与目标状态，可省略>

保持不变：
- <已经正确的部分>
- <已经正确的部分>

不要重新设计整个 Logo。
不要增加参考图中不存在的内容。
不要改动未列入本轮修正项的正确部分。
继续匹配原图的构图、文字、颜色、比例、位置、间距和视觉效果。
```

每轮只填写 1—3 个高优先级差异，并明确列出保持不变项。修改前重新执行“生图前确认”。

## 基础验收清单

对照 Image 1 检查当前稿，仅检查以下必要项目：

- 元素是否完整
- 文字是否逐字准确
- 构图和比例是否匹配
- 颜色和视觉效果是否一致
- 位置和间距是否合理
- 背景和画布比例是否匹配
- 是否出现多余内容

验收后只选择最明显的 1—3 个差异进入下一轮，不提出无关创意建议。

## 标准执行步骤

1. 接收用户拥有或获准使用的参考 Logo，并确认本次输出要求。
2. 使用 `imagegen` Skill 分析参考图和整理需求，不先生成图片。
3. 提出候选输出参数并等待用户确认；确认后填写最终提示词、汇总完整生图方案，再等待用户回复“开始生图”。
4. 获得本次授权后，使用 `gpt-image-2` 生成一张首稿。
5. 按基础验收清单对照参考图，找出最明显的 1—3 个差异。
6. 使用通用修正提示词列出修正项和保持不变项，重新汇总方案并重新等待“开始生图”。
7. 每次只生成一张修正稿，重复验收与授权流程，直到用户确认成品。
8. 保存用户确认的成品；不要再用模型重新生成已确认的主文件。
9. 把案例独有问题和经验记录在项目的案例工作台，不写入本 Skill。

## 通用经验更新规则

- 始终维护同一个 Skill，不设置人为版本号。
- 只有确认能够跨不同 Logo 案例复用的规则，才更新本 Skill。
- 单个案例的元素、视觉特征、修正细节和偶发现象，只记录在对应案例工作台。
- 新经验应保持简短、可执行，并放入最相关的现有章节。
- 不为尚未出现的需求提前增加分类、复杂结构、脚本或资源目录。
- 每次更新后运行 Skill 校验，确保 frontmatter、目录和元数据仍然有效。
